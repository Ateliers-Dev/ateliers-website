# ドキュメント作成ガイドライン

## 1. 概要

Ateliers では、人間と AI が協働してプロダクトの開発・保守・改善を行います。

ドキュメントは、プロダクトの利用者が機能を理解するためだけでなく、開発者や AI エージェントが仕様を正しく理解し、継続的に開発を進めるための情報資産でもあります。

そのため、ドキュメントの目的と対象読者を明確にし、適切な粒度で情報を整理します。

本ガイドラインは、Ateliers におけるドキュメントの分類、記述方針、管理方法の共通基準を定めるものです。

### 基本方針

- ドキュメントの目的と対象読者を明確にする。
- 読者が必要な情報を見つけやすい構造にする。
- 内容の正確性を重視し、事実と推測を区別する。
- 実装済みの機能と、計画・検討段階の機能を区別する。
- 同じ情報の不必要な重複を避け、関連文書を相互に参照できるようにする。
- 文書の作成・維持そのものを目的とせず、必要な情報を必要な粒度で提供する。
- 最初から完全な体系を目指さず、開発や運用を通じて改善する。

## 2. ドキュメントの分類

Ateliers では、ドキュメントを目的と情報の粒度によって分類します。

当面は、以下の2種類を基本分類として運用します。

| 分類 | 目的 | 主な対象読者 |
| --- | --- | --- |
| Feature | プロダクトが何をできるのかを説明する | 利用者、開発者、関係者 |
| Reference | プロダクトの仕様や仕組みを正確に説明する | 開発者、保守担当者、AI エージェント |

将来的な分類として Manual も想定しますが、現段階では独立した分類としての運用を必須としません。

### 2.1. Feature

**Feature は、プロダクトが提供する機能、特徴、利用価値、制約を説明するドキュメントです。**

主に「何ができるのか」「どのような目的で提供されるのか」という疑問に答えます。

開発者以外の読者にも理解できることを重視し、可能な限り平易な表現を使用します。

ただし、初心者向けの文書であることを意味するものではありません。必要な技術用語は使用できますが、内部実装の知識がなくても機能を理解できることを目指します。

#### 記載する情報

- 機能の概要と目的
- 解決する課題
- 提供する機能と特徴
- 想定される利用場面
- 利用することで得られる価値
- 利用上の制約や注意事項
- 関連する機能やドキュメント

#### 記述方針

- 機能と利用者の視点を中心に説明する。
- 内部構造や実装技術の詳細は、原則として Reference に委ねる。
- 技術用語は必要に応じて使用し、理解に必要な説明を補う。
- 実装済みの機能と、開発中・計画中の機能を混同しない。
- 機能の制約や未対応事項も必要に応じて明示する。
- 文章だけでは理解しにくい場合は、図や画像を活用する。

#### 記述例

**AI オーケストレーション**

AI オーケストレーションは、複数の AI エージェントが役割を分担し、ソフトウェア開発の作業を進めるための仕組みです。

人間が作業の目的や条件を指定すると、AI エージェントが調査、実装、テスト、レビューなどを分担して実行します。

これにより、人間はすべての作業工程に直接介入するのではなく、作業の委譲と最終的な判断に集中できます。

作業結果や問題は記録され、人間が後から確認できるようにします。

この説明では、機能と目的を中心に記載し、タスク定義の JSON 構造や内部実装には立ち入りません。

### 2.2. Reference

**Reference は、プロダクトの設計、仕様、設定項目、内部構造などを正確に説明する技術ドキュメントです。**

主に「どのような仕様なのか」「どのような仕組みで動作するのか」という疑問に答えます。

開発者や保守担当者だけでなく、AI エージェントが実装や修正を行う際の参照資料として利用することも想定します。

そのため、読みやすさに加え、技術的な正確性、具体性、一貫性を重視します。

#### 記載する情報

- システムやコンポーネントの設計
- アーキテクチャと責務
- データ構造とスキーマ
- API やインターフェースの仕様
- 設定項目とパラメータ
- 処理フローと状態遷移
- 入力条件、出力結果、例外処理
- 制約事項と技術的な前提条件
- 実装や検証に必要な技術情報

#### 記述方針

- 技術的な正確性を優先する。
- 用語、識別子、パラメータ名を統一する。
- 必要に応じてコード、JSON、表、図などを使用する。
- 入力値、初期値、必須条件、制約条件を明確にする。
- 実装によって保証される動作と、設計上の期待を区別する。
- 未実装の仕様や検討中の設計は、その状態を明示する。
- 実装の変更によって仕様が変わった場合は、関連する文書も更新する。

#### 記述例

**オーケストレーターのタスク定義仕様**

オーケストレーターは、JSON 形式のタスク定義を受け取り、指定された条件に従って作業を実行します。

タスク定義には、目的、作業範囲、要求事項、受け入れ基準、委譲操作、停止条件などを記述します。

例えば、以下のようなフィールドを使用します。

| フィールド | 説明 |
| --- | --- |
| `purpose` | タスクの目的 |
| `requirements` | 実現すべき要求事項 |
| `acceptanceCriteria` | 完了・合格と判断する条件 |
| `delegatedOperations` | 委譲する操作 |
| `stopConditions` | 作業を停止する条件 |

正式な Reference では、これらに加えて、データ型、必須・任意、初期値、制約条件、実行時の解釈などを記載します。

なお、上記は記述形式を示す例であり、実際のスキーマ仕様は実装と照合して確定します。

## 3. Feature と Reference の関係

Feature と Reference は、同じプロダクトや機能について異なる視点から説明するドキュメントです。

同じ対象について両方を作成しても構いません。

例えば、AI オーケストレーションについて、以下のように分類できます。

| 説明する内容 | 分類 |
| --- | --- |
| AI オーケストレーションで何ができるか | Feature |
| 複数の AI エージェントが協働する目的 | Feature |
| 利用者が期待できる成果と制約 | Feature |
| タスク定義 JSON のフィールド仕様 | Reference |
| エージェント間の情報受け渡し | Reference |
| 状態遷移や停止条件の詳細 | Reference |
| 実行証跡のデータ構造 | Reference |

### 3.1. 情報の重複を避ける

Feature と Reference の両方で、同じ詳細仕様を繰り返し記載することは原則として避けます。

Feature では機能の概要を説明し、詳細な仕様が必要な場合は Reference を参照します。

Reference では仕様を中心に記載し、機能の背景や利用価値については Feature を参照します。

### 3.2. 相互参照

関連する Feature と Reference が存在する場合は、可能な限り相互にリンクします。

例えば、Feature には「詳細な技術仕様」、Reference には「機能概要」へのリンクを設けます。

これにより、読者は目的に応じて必要な情報へ移動できます。

### 3.3. 両方の作成を必須としない

すべての機能について、Feature と Reference の両方を作成する必要はありません。

単純な機能であれば Feature だけで十分な場合があります。

一方、内部的な設定項目やデータ構造などは、Reference だけで十分な場合もあります。

文書の数を増やすことではなく、必要な情報を適切に提供することを優先します。

## 4. Manual の位置付け

Manual は、プロダクトの導入、設定、操作などを、具体的な手順に沿って説明するドキュメントとして想定します。

主に「どのように使用するのか」という疑問に答えます。

例えば、以下のような内容が該当します。

- インストール手順
- 初期設定
- 操作方法
- タスクの実行手順
- トラブルシューティング

Feature が「何ができるか」、Reference が「どのような仕様か」を説明するのに対し、Manual は「どのように操作するか」を説明します。

ただし、当面は Feature と Reference の2分類を基本とします。

操作手順が必要な場合は、適切な文書に含めるか、独立した文書として管理します。

Manual の独立した分類は、文書量や利用状況に応じて将来検討します。

## 5. 既存の技術ドキュメントとの関係

Ateliers では、プロダクトの説明とは別に、技術方針や技術情報も管理します。

それぞれの文書は、次の目的で区別します。

| 分類 | 主な目的 |
| --- | --- |
| Technical Policies | 技術的な判断基準や開発方針を説明する |
| Technical Notebook | 技術的な知識、調査結果、学習内容を記録する |
| Feature | プロダクトが提供する機能を説明する |
| Reference | プロダクトの具体的な仕様や設計を説明する |

### 5.1. Technical Policies との違い

Technical Policies は、設計や開発において、どのような方針で判断・実施するかを説明します。

一方、Reference は、特定のプロダクトがどのような仕様で設計・実装されているかを説明します。

例えば、例外処理に関する共通方針は Technical Policies に該当します。

特定の API が返すエラーコードや例外条件は Reference に該当します。

### 5.2. Technical Notebook との違い

Technical Notebook は、技術的な知識や調査結果を記録するための文書です。

一方、Reference は、特定のプロダクトの仕様を参照するための文書です。

例えば、JSON Schema の一般的な使い方を解説する記事は Technical Notebook に該当します。

Ateliers のオーケストレーターが受け付ける JSON Schema の正式仕様は Reference に該当します。

### 5.3. 文書の役割を混同しない

技術的な知識、開発方針、プロダクトの機能、プロダクトの仕様は、それぞれ異なる目的を持ちます。

文書を分類する際は、記載されている技術の種類ではなく、**その文書が何を伝えるために存在するか**を基準とします。

## 6. ドキュメントの正確性と更新

### 6.1. 事実と計画を区別する

ドキュメントでは、実装済みの内容と、開発中・計画中の内容を明確に区別します。

未実装の機能を、現在利用可能な機能として説明してはいけません。

必要に応じて、以下のような状態を明示します。

- 実装済み
- 開発中
- 計画中
- 検討中
- 非推奨
- 廃止

これらは文書の状態を表すための例であり、すべての文書に状態の記載を義務付けるものではありません。

### 6.2. Reference と実装の整合性

Reference は、原則として対象プロダクトの実装と整合している必要があります。

実装の変更によって仕様が変わる場合は、関連する Reference の更新も検討します。

ただし、Reference に将来の設計案を記載することは禁止しません。

その場合は、現行仕様と将来の設計案を明確に区別します。

また、Reference に記載されている内容であっても、実装による保証が確認できないものを、保証済みの動作として扱ってはいけません。

### 6.3. Feature と実際の機能の整合性

Feature では、利用者が期待できる機能と、実際に提供される機能の整合性を重視します。

実装の変更によって機能が追加・変更・廃止された場合は、関連する Feature の更新も検討します。

内部実装だけが変更され、利用者から見た機能や制約が変わらない場合は、必ずしも Feature を更新する必要はありません。

### 6.4. AI エージェントによる参照

AI エージェントがドキュメントを参照する場合も、人間と同じく文書の目的と適用範囲を尊重します。

特に Reference については、以下を考慮します。

- 対象プロダクトとバージョンを確認する。
- 実装済みの仕様と設計案を区別する。
- 不明な仕様を推測によって確定しない。
- 文書と実装に矛盾がある場合は、その内容を報告する。
- 文書に記載がないことだけを理由に、機能が存在しないと断定しない。

なお、Reference は技術仕様を説明する資料であり、それ自体が AI エージェントへの操作権限を付与するものではありません。

AI エージェントの行動や操作権限は、適用される作業指示や実行環境の制約に従います。

## 7. ドキュメントの構成と管理

### 7.1. ファイル構成

ドキュメントは、原則として目的に応じた分類で整理します。

例えば、単一プロダクトでは次のような構成が考えられます。

```text
docs/
├── features/
│   ├── overview.md
│   └── orchestration.md
│
└── reference/
    ├── overview.md
    └── task-definition.md
```

これは構成例であり、すべてのリポジトリに同一のディレクトリ構造を強制するものではありません。

プロダクトの規模、既存の構成、Docusaurus との連携方法などを考慮して決定します。

### 7.2. ファイル名と分類名

分類名として、以下の英語表記を使用します。

- `Feature`
- `Reference`
- `Manual`（将来の分類）

ディレクトリ名については、複数形の `features`、単数形の `reference` など、既存のリポジトリの命名規則との整合性を優先します。

分類の概念と物理的なディレクトリ名は、必ずしも完全に一致する必要はありません。

### 7.3. Docusaurus での記述

Docusaurus に掲載する Markdown では、必要に応じて Front Matter を使用します。

例えば、次のように記述します。

```yaml
---
title: タスク定義仕様
description: オーケストレーターのタスク定義JSONの仕様を説明します。
---
```

文書のタイトルは、内容を具体的に表すものとします。

「Reference 1」「機能説明」など、分類だけでは内容が判断できないタイトルは避けます。

### 7.4. 文書の分割

文書が大きくなった場合は、目的や責務に応じて分割します。

ただし、短い文書を過度に細分化することは避けます。

関連性の高い情報は、読者が一連の内容として理解できる構成を優先します。

## 8. ドキュメント作成時の判断基準

新しい文書を作成する際は、次の順序で判断します。

1. **目的を確認する。**  
   何を伝えるための文書なのかを明確にする。

2. **対象読者を確認する。**  
   利用者、開発者、保守担当者、AI エージェントなど、主な読者を想定する。

3. **分類を選択する。**  
   機能説明なら Feature、技術仕様なら Reference を基本とする。技術方針や一般的な技術情報は、既存の分類との関係も確認する。

4. **既存文書を確認する。**  
   同じ情報がすでに存在する場合は、更新や相互参照を検討する。

5. **必要な粒度で記述する。**  
   読者に必要な情報を優先し、過剰な詳細や不要な重複を避ける。

6. **内容の正確性を確認する。**  
   仕様、実装、計画の状態を区別し、不明な情報を推測で確定しない。

7. **関連文書との関係を整理する。**  
   必要に応じて Feature、Reference、その他の文書を相互参照する。

## 9. ガイドラインの改善

本ガイドラインは、ドキュメントの品質と保守性を高めるための共通基準です。

すべてのケースを最初から想定し、厳密な分類や構造を強制することは目的としません。

実際の開発や運用において、分類が不明確になった場合や、新しい文書の種類が必要になった場合は、その都度検討します。

また、分類の追加や構成の変更によって得られる利点と、管理上の負担を比較し、必要性に応じて改善します。

**ドキュメントは、作成すること自体が目的ではありません。人間と AI が正確な情報を共有し、より良い成果を生み出すためのものです。**
