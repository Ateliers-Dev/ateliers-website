# SQLite データ所有権と共有契約

> 作成日: 2026-11-23
> 更新日: 2026-11-23
> 作成者: Codex

## 「見える」「読める」「書ける」「所有する」を区別する

同じ Windows ユーザー領域にある DB を別アプリが開けることは、そのアプリにデータの所有権や更新権があることを意味しません。共有とは物理的なファイルアクセスではなく、データセットの意味、責任者、利用可能な操作、互換性を合意した状態です。

| 責務 | アプリケーション固有 DB | 横断共有 DB |
|---|---|---|
| データの業務上の所有者 | 当該アプリ | データセットごとに指定する一つの論理所有者 |
| スキーマ定義・マイグレーション | 当該アプリの所有チーム | 共有データセット所有者。利用側が独自変更しない |
| 書き込み | 当該アプリが所有境界で行う | 指定された書き込みサービスまたは契約上の単一 writer が行う |
| 他アプリからの利用 | 明示的なエクスポート、API、または読取専用契約 | 登録済み利用者に、契約で許した操作を提供 |
| バックアップ・復元・保持 | 当該アプリの責務 | データセット所有者の責務。利用者に復旧条件を通知 |
| 廃止 | アプリとデータの削除方針に従う | 利用アプリの移行・退役を確認し、所有者がライフサイクルを決める |

「単一の論理所有者」は必ずしも一つのプロセスとは限りません。複数プロセスが直接ファイルへ書く場合は、SQLite の単一 writer 制約を踏まえた調停、再試行、障害対応を別途設計します。所有者が不在・廃止になる場合に備え、後任への責任移管方法も定めます。

## 共有データセットの契約

共有 DB を作成・公開する前に、データセット単位で次の項目を合意し、バージョン管理された契約として保管します。

1. 安定した dataset ID、目的、データ所有者、問い合わせ先、後任・退役手続き。
2. 含むデータ、含まないデータ、分類、機密性、個人情報の有無、データの正本か派生物か。
3. 利用側の一覧、認可する主体、読取・追加・更新・削除の操作境界。
4. スキーマのバージョン、互換性規則、廃止予定、マイグレーションの調整方法。
5. 書き込み担当、重複排除 ID、冪等性、競合と失敗の応答、再試行条件。
6. 保持期間、削除・エクスポート、バックアップと復元、容量上限、障害時の連絡・復旧責任。
7. 必要な記録完全性の水準、欠損検出方法、監査用途の可否と限界。
8. 利用アプリが契約終了・削除される場合の影響と、データの継続管理者。

契約がない DB の内部テーブルへ別アプリが直接書き込むことを、共有の実現方法として採用しません。まず利用 API または限定されたデータ操作の境界を検討します。契約を備えた直接 DB 接続を選ぶ場合も、スキーマ変更の権限は所有者に残し、接続先パスやテーブル実装を利用側に散在させません。

## 接続方式は未決定

将来のクライアントと SQLite の間には、少なくとも次の二案を維持します。

| 案 | 利点 | 設計時に確認すること |
|---|---|---|
| MCP から SQLite へ直接接続 | 常駐サービスや追加導入手順が不要になり得る。ローカル実行が簡潔。 | DB ファイルへの権限が広くなりやすい。利用者・プロセスごとの認可、競合、スキーマ露出、接続の寿命、同時更新をどう制御するか。 |
| MCP からローカル API を介して SQLite へ接続 | データ操作を契約化し、認可・検証・書き込み調停・将来の保存先変更を境界に集約しやすい。 | サービスの起動・配布・障害・認証・ポートや IPC の保護が追加され、利用者の手順が煩雑になる可能性。 |

どちらも採用済みの構成ではありません。共通要件は保存方式に依存しない識別子とデータ契約で表現し、MCP クライアントには DB パスや内部スキーマを固定公開しません。将来の比較では、利用者の導入容易性、権限境界、同時実行、監査、配布・更新、障害復旧、別ストア移行の影響を評価します。
