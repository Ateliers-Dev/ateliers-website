# SQLite ローカル DB の運用・完全性・セキュリティ

> 作成日: 2026-11-23
> 更新日: 2026-11-23
> 作成者: Codex

## トランザクションと同時書き込み

SQLite は一つのデータベースファイルへの書き込みを直列化し、同時に進められる writer は一つです。複数接続が書く場合も自動で順番待ちになるとは限らず、ロック競合などで `SQLITE_BUSY` を返すことがあります。実装では次を定めます。

- トランザクションを短くし、ネットワーク、利用者入力、長時間計算を開いたままのトランザクション内で待たない。
- 書き込みの調停担当を決める。イベントを複数 producer が生成する場合、取り込み時に重複排除 ID、順序、再送可能性を定義する。
- busy timeout と再試行の上限・間隔を明示し、無期限に待たない。再試行は冪等な単位に限り、失敗や未確定状態を隠さない。
- 同じ DB を開く接続の数、寿命、トランザクション境界、複数プロセスの有無を実運用条件で検証する。
- 書き込み量が継続的に集中し、競合待ちや遅延が許容範囲を超える場合は、単一 writer キューやローカル API、別の永続化方式を評価する。

## WAL の用途と制約

WAL は読み取りと書き込みが並行できる利点がありますが、writer は引き続き一つです。WAL を選ぶ場合、アプリ要件と配布 SQLite バージョンを確認し、次を扱います。

- SQLite は DB と同じ場所に `-wal` と `-shm` を作ることがあります。WAL はコミット済みデータを含み得る DB の永続状態です。稼働中に DB 本体だけをコピー・移動・削除せず、WAL や SHM を Temp と同じ清掃対象にしません。
- 読み取り接続を長時間開いたままにすると checkpoint が進まず WAL の縮小を妨げる可能性があります。チェックポイント方針、接続終了、容量監視、障害後の回復を設計します。
- WAL は、同じホスト上のプロセス間で共有する用途を前提とし、ネットワークファイルシステム越しの共有には使いません。
- すべての SQLite 接続で採用するジャーナル方式と互換性をそろえ、接続ごとの設定漏れを確認します。
- SQLite の修正版を配布・更新する責任を定めます。WAL の破損に関わる既知の修正を含め、採用時点の公式リリース情報・修正履歴を確認し、古い組み込み版を無条件で使い続けません。

WAL は候補の運用方式であり、すべてのローカル DB への一律の強制ではありません。実際の読み取り比率、書き込み競合、障害復旧、利用中の SQLite ビルドに基づいて決定します。

## バックアップ、復元、整合性確認

- オンライン中の DB では SQLite の Online Backup API、または条件に合う一貫性のある手段を使用します。WAL 利用中に DB 本体だけをファイルコピーして、完全なバックアップとみなしません。
- バックアップを一時名へ作成し、処理成功と整合性確認を経てから確定します。保存先の容量、アクセス制御、暗号化の要否、世代数、保持期限を決めます。
- バックアップの成功記録には対象 DB ID、スキーマ版、取得時刻、方法、完全性確認の結果を含めます。バックアップの存在だけで復元可能とは断定しません。
- 定期的に別パスへ復元し、SQLite の整合性検査、必要に応じた外部キー検査、アプリケーションからの読み取り、スキーマ版・期待件数などの業務検査を実施します。検査で問題があれば復旧完了と扱いません。
- 許容データ損失量と復旧時間の要件があるデータは、その目標に合う取得頻度と復元手順を設定します。重要度が未確定なら値を共通標準として決めず、実装前の判断事項として記録します。
- Temp、キャッシュ、診断ログ、監査記録の各保持規則をバックアップ保持へ無条件に転用しません。監査証跡を含めるか、削除要求とバックアップ世代をどう扱うかを別途定めます。

## マイグレーションと互換性

DB スキーマ版とアプリのリリース番号を分離し、使用する SQLite の `user_version` など明示的なスキーマ管理手段を選びます。DB の用途を検出する必要がある場合は `application_id` などを使って誤った DB のオープンを防ぐ方法を検討します。これらの pragma の使用自体や値は実装段階で決定します。

マイグレーションでは、実行前に DB の種類・スキーマ版・互換範囲を検査し、必要ならバックアップを取り、1回の移行の原子性、完了版の更新、再起動後の再試行、失敗時の復旧を定めます。サポートしない将来版を古いプログラムが開いて書き換えないようにします。移行後はスキーマ整合性と代表的な読み書きを確認します。元 DB は移行成功と復元可能性が確認できる前に削除しません。

## 記録完全性と監査保証の水準

「SQLite にイベントが保存される」ことと「監査証跡として完全で改ざんを検出できる」ことは別の保証です。データセットごとに、目的に合う保証レベルを記録します。

| 水準 | 例 | 扱い |
|---|---|---|
| 診断 | ローテーション可能な運用ログ | 障害調査用。欠落・削除があり得る。監査証跡として使用しない。 |
| 分析 | 実行 ID、イベント ID、時刻、順序、終端状態、取り込み・永続化状態を持つイベント | 欠番・重複・終端記録の欠落を表現し、不完全な実行を正常完了に見せない。記録漏れや同一信頼境界での改変を防げるとは限らない。 |
| 保護された監査 | 明示した脅威モデルに基づくアクセス制御、独立した検証・保管境界、鍵管理などを備えた証跡 | 保証した脅威と保証しない脅威、検証者、保存・削除・復元手順を定義し、対象環境で検証する。ローカル DB だけで改ざん不能・非否認性を主張しない。 |

分析記録では、実行の終端状態、イベント順序または連番、欠番検出、発生時刻と永続化時刻の意味、記録が受理・キュー登録・永続化されたどの時点で成功と応答するかを契約化します。終端記録がない実行は未完了または状態不明として扱います。ハッシュや署名を使う場合も、鍵・検証手順・保護境界が記録者の書き換え権限から独立しているか検討します。

## セキュリティとプライバシー

- ローカル DB の ACL は最小権限とし、保護を同じユーザー権限で動く他プロセスへの防御と同一視しません。端末利用者自身の悪意ある改変、管理者権限、バックアップ流出への保証が必要なら追加の保護境界を設計します。
- SQLite の標準ライブラリは DB ファイルを暗号化しません。ディスク暗号化を利用する場合も、対象端末・ユーザー・バックアップ・WAL の脅威モデルを確認します。DB 単位の暗号化が必要なら、採用する実装の互換性、鍵の作成・保管・ローテーション・復旧、DB・WAL・一時領域・バックアップの保護範囲を別途選定・検証します。暗号化機能の有無を SQLite という製品名だけから仮定しません。
- 資格情報、秘密鍵、不要なプロンプト・会話本文、個人情報を記録しません。保存目的がある場合は分類、権限、秘匿化、暗号化、保持・削除・エクスポートを定義します。
- DB ファイル、バックアップ、WAL をログへ添付・出力するときは、含まれる情報とアクセス範囲を確認します。
- 外部入力を SQL 文字列へ連結せず、パラメーター化クエリを使います。共有 DB の操作は公開契約で許可した範囲に絞ります。
- 不正なファイル、誤った `application-id`、未知のスキーマ版、書き込み不能、ディスク不足、DB 破損、復元失敗を安全に処理し、空 DB で既存データを上書きしません。

## Temp との境界

DB 本体と WAL は、WAL 利用時にコミット済みデータを保持し得る永続状態です。SHM とロールバックジャーナルは稼働中の SQLite が使う補助ファイルであり、終了後の寿命や再生成可能性は方式・状態により異なります。いずれも稼働中に Temp の一般清掃で削除してはいけません。移行中の必要データと検証対象のバックアップも、所有者が安全に不要と確認するまで一時データとして期限削除しません。親の[一時データと容量管理](../temporary-data.md)の上限・期限を、これらのファイルへ適用しません。

SQLite API が不要と確認した後に限り、SQLite が管理する一時作業ファイルや所有が確認できる中断済み移行生成物を回収します。稼働中 DB の隣接ファイルを拡張子だけで判断して削除しません。
