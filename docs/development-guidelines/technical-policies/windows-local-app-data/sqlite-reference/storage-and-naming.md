# Windows ローカル SQLite の配置・識別・命名

> 作成日: 2026-11-23
> 更新日: 2026-11-23
> 作成者: Codex

## 適用範囲と保存領域

この方針は、同一 Windows ユーザーの端末内で使用する SQLite データを対象にします。通常の配置先は Windows API から解決した `%LOCALAPPDATA%` 配下です。環境変数を文字列として連結して実パスを求めず、親リファレンスの[保存場所とデータ分類](../storage-layout.md)に従います。

SQLite のデータベース、WAL、共有メモリ、ロールバックジャーナルなど、稼働中に必要な関連ファイルを Temp やキャッシュへ分離しません。ネットワーク共有や同期フォルダー上で SQLite/WAL を共有することを標準方式にしません。

## アプリケーション固有データと共有データ

保存場所に加え、所有者と書き込み契約で二種類を区別します。

| 区分 | 定義 | 初期配置案 | 書き込み責任 |
|---|---|---|---|
| アプリケーション固有 DB | 一つのアプリケーションの機能・内部状態が所有するデータ。ほかのアプリが読める必要があっても、そのことだけでは共有 DB にならない。 | `%LOCALAPPDATA%\Ateliers-Dev\<application-id>\data\<database-id>.sqlite3` | 所有アプリだけがスキーマを管理し、書き込む。ほかの利用者は明示した読み取り境界を通じて利用する。 |
| 横断共有 DB | 複数アプリが共通の意味・ライフサイクルを持つデータセットとして、契約に基づき利用するデータ。単に同じファイルを開ける状態ではない。 | `%LOCALAPPDATA%\Ateliers-Dev\shared\<dataset-id>\<database-id>.sqlite3` | データセットごとに指定した単一の論理所有者がスキーマと書き込み規則を管理する。利用アプリには契約で定めた操作だけを許す。 |

パスは論理配置案です。アプリ固有 DB は既存の製品別ディレクトリを活用でき、共通領域への一括移動を要求しません。共有領域は、共有要件と所有者が確立したデータセットに限って設けます。

## ディレクトリ案の比較と選択

| 案 | 長所 | 注意点 |
|---|---|---|
| 既存の製品別ディレクトリを継続 | 既存データ、アップデーター、利用者の期待との互換性が高い。 | 製品改名に備え、論理 ID と実パスを分離して記録する。新規の共有 DB はここへ暗黙に置かない。 |
| 組織配下にアプリ別・共有別の論理スコープを設ける | 新規アプリと真に共有するデータの責任境界が見やすく、名前の衝突を避けやすい。 | 既存データを一斉移行せず、新しい階層を導入する必要性をデータセットごとに確認する。 |
| 一つの製品ディレクトリへ共有 DB も集約 | 配置箇所が一つで、初期実装が簡単。 | その製品が所有者と見なされやすく、製品の削除・改名・権限変更が他アプリのデータに波及する。明示的な所有契約なしでは採用しない。 |

**新規設計の推奨:** アプリ固有 DB は既存または製品固有の安定したアプリルートを使います。将来、複数アプリが同じデータセットを共有する実要件ができた場合だけ、その所有者が管理する独立した共有領域を追加します。`apps/shared` は検討可能な命名例に留め、全アプリの保存先再編を規定しません。

## 既存保存先との互換性と移行

- すでに利用者データが保存されている場合、物理パスを変えずに論理 ID と DB 命名を適用できるか先に評価します。
- 既存データがある DB を新しいパスへ暗黙に複製・移動・作り直しません。移行が必要なら、送信元の検出、バックアップ、移行先検証、完了記録、再試行、ロールバックまたは復旧、旧データの保持期間を個別に定義します。
- 旧 DB と新 DB の双方が書き込み可能になる期間を避けます。二重書き込みを採る場合は、重複・順序・失敗時の照合方法を設計し、移行完了条件を明示します。
- 移行後も古いバックアップの復元と旧版起動があり得ます。旧版が新スキーマを書き換えない互換条件と、復旧後のバージョン確認を定めます。
- パス移行をしない選択も可能です。保存パスの別名・バージョン履歴をアプリ側で扱い、安定 ID が同じ保存先の再発見を助ける方式を検討します。

詳細は[作成・更新・削除と移行](../lifecycle.md)を参照してください。

## 安定 ID と命名規則

リポジトリ名は初回の識別子候補を得る手段として便利ですが、データの永続 ID にはしません。初回リリースや利用者データ作成前に、製品の論理的な同一性に基づいて ID を決めます。ID は小文字 ASCII の英数字とハイフンで表す短い kebab-case を基本とし、組織内で衝突しない名前空間とします。

- `application-id` はアプリのデータ所有者を識別します。リポジトリの改名・移管、表示名変更、実行ファイル名変更、発行者表記の変更では変更しません。
- `dataset-id` は横断共有データセットの意味と責任境界を識別し、作成時に所有者・利用者・契約と共に登録します。
- `database-id` は一つのアプリまたはデータセット内の DB を識別します。単一 DB なら `main` など明確な固定値を使い、ファイル名を `<database-id>.sqlite3` とします。
- ID を変更する必要が生じたら、同じデータの別名として明示し、移行記録を残します。新 ID の DB を無関係な新規データとして作って既存データを見失わせません。

ID はバージョン番号、環境名、ブランチ名、端末名を含まない安定部分とします。Debug/Release や開発・本番の分離が必要な場合は、親方針に沿った明示的な環境スコープを別のパス要素として設けます。環境分離は論理アプリ ID の改名を意味しません。

実際のパスは設定・配置コンポーネントから解決し、各 DB クライアントに文字列パスを重複定義しません。パスが環境設定で変更された場合は、既存データの所在・移行状態・書き込み可能な実体を確認します。

次章は[データ所有権と共有契約](./ownership-and-contracts.md)を説明します。
