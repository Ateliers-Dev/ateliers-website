# Windows ローカルデータ管理の概要

> 作成日: 2026-11-23
> 更新日: 2026-11-23
> 作成者: Codex

## 目的と適用範囲

Windows アプリケーションが設定、永続データ、診断ログ、実行記録、監査証跡、キャッシュ、一時データをユーザー領域へ保存するときの共通方針を示します。将来、AI 協働における実行記録・分析・改善・監査に活用できるデータ基盤を目指します。本書は Windows 専用の技術リファレンスです。

本文では、個別実装の調査で観測した内容と、今後の共通化に向けた推奨方針を区別します。観測結果は現行実装の例であり、標準ではありません。推奨方針は今後の設計基準として示します。製品に適用する際は要件、リスク、既存データへの影響を確認してください。

## 既存実装で観測したこと

| 観点 | 観測した例 |
|---|---|
| ユーザー単位の領域 | .NET の `Environment.SpecialFolder.LocalApplicationData` を使い、端末固有のデータをユーザー単位の Local 領域に置く実装がある。 |
| 設定と端末固有データ | デスクトップアプリの一例では、設定を Roaming 領域、端末固有データを Local 領域に分けている。Debug と Release でも別の保存先を使う。 |
| 永続データ | 端末固有データ配下に SQLite ファイルを置き、会話や記事の情報を保存する例がある。ここではデータベースの設計内容を評価・規定しない。 |
| 診断ログ | Local 領域のログをサイズでローテーションし、世代数を制限する例がある。 |
| 実行記録 | CLI の例では、既定のユーザー単位 Local 領域に実行ごとのイベント記録とレポート、ライフサイクル記録を保存し、引数で出力先を変更できる。 |
| 一時データ | 個別の Temp 管理ではファイル数・総容量・有効期間を制限し、使用中のファイルを避けて清掃する。詳細と数値例は[一時データと容量管理](./temporary-data.md)に記載する。 |
| 旧保存先 | ある CLI の利用者向け説明では、旧保存先のデータを自動移動・削除しないとしている。これはその製品固有の扱いである。 |

この表は調査対象のコードと説明で確認した範囲です。利用者の端末に実データが存在するか、全リリースで挙動が同じか、過去に作られた残存データがあるかまでは確認していません。製品名やソースの所在に依存しないよう、具体的な製品名とリポジトリ名は記載していません。

## 今後の共通方針

1. データの性質と必要な寿命から保存領域を選び、アプリケーション固有のルートと用途別ディレクトリを使います。
2. 端末固有の永続データ、診断ログ、監査証跡、キャッシュ、一時データを分類し、それぞれの保持・削除・復旧方針を定めます。
3. 保存先を一か所に集約して解決し、フォルダーは書き込みが必要になった時点で作成します。
4. ビルド構成、実行環境、データセットの識別を混同せず、開発データが利用者のデータを読み書きしないよう分離します。
5. 更新・削除・形式変更では、失敗時の復旧と既存データの互換性を考慮し、暗黙に利用者データを捨てません。
6. キャッシュと一時データの増加には上限を設け、安全な清掃を行います。
7. 将来の分析・監査に使う記録は、通常の診断ログとは目的・保持・アクセス制御を分けます。

保存領域の選び方は[保存場所とデータ分類](./storage-layout.md)、データの寿命と移行は[作成・更新・削除と移行](./lifecycle.md)、実行記録・分析・監査の考え方は[実行記録と監査データ](./records-and-audit.md)、短命データは[一時データと容量管理](./temporary-data.md)を参照してください。

## SQLite と将来のアクセス方式

SQLite は将来のローカル記録基盤の候補として見据えますが、この Reference ではプロバイダー、スキーマ、同時アクセス、バックアップなどの具体的な仕様を決めません。MCP から SQLite へ直接アクセスする案と、MCP からローカル API を介して SQLite へアクセスする案のどちらも構想であり、現段階では選定しません。詳細は[実行記録と監査データ](./records-and-audit.md)を参照してください。
