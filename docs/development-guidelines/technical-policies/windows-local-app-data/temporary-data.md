# Windows 一時データと容量管理

> 作成日: 2026-11-23
> 更新日: 2026-11-23
> 作成者: Codex

## 既存実装で確認した Temp 管理

調査したデスクトップ実装の Temp 管理コードは、Local のアプリケーション領域に `temp\v1\<owner-id>\<purpose>\` を作ります。用途は画像、音声用、一般作業用に分かれ、Temp ストアの既定値は**最大64ファイル、合計256 MiB、最長30分**です。音声用の用途区分があることは、音声機能が実装済みであることを意味しません。

確認できた容量肥大化防止・清掃処理は次のとおりです。

- ファイル作成前に容量と件数を確認し、同時作成に備えて予約ファイルを置きます。予約容量を超えた入力は拒否され、未確定の `.part`、予約、確定マーカーは作成失敗時に回収を試みます。
- 上限に達した場合、使用中でない古いファイルから空きを作ります。期限切れでも使用中のファイルは削除しません。
- 各プロセスの owner ディレクトリをファイルロックで保護します。ロックを取得できないディレクトリは使用中または安全性が不明なものとして回収対象にしません。終了済み owner の残存ファイルは、次の清掃でロックを取得できたときに回収します。
- ワーカー起動時に清掃を開始し、3秒以内の待機を試みます。清掃の失敗は診断ログへ記録して継続します。作成処理の完了後にも清掃を呼び出し、利用者は自プロセスの未使用ファイルを明示的に削除できます。
- 清掃はロックと使用権を確認しながら進みます。強制終了・OS停止時に即時清掃が完了する保証はなく、残存データは後続起動時の回収対象になります。

ここで示した数値は調査した実装の既定値です。Ateliers 全体の標準値として決定済みではありません。また、この上限は当該 Temp ストアが管理するデータに対するもので、`%TEMP%` や他アプリケーションのファイル、ディスク全体の使用量を制限するものではありません。

## 推奨する Temp 方針

一時データを保存する機能は、実装前に用途と保護期間を定義し、次の上限を設定します。

- 最大ファイル数
- 合計バイト数
- 1件あたりの最大バイト数
- 保持期間
- 同時処理分を含めた容量予約の方法

数値は対象データと利用者の作業時間に合わせて決め、無制限の成長を許しません。設定値を無効な状態で起動するより、起動時に検出して保存機能を拒否するか、安全な値に制限します。

Temp の保存先は、キャッシュや永続データと分けたアプリケーション固有の `temp` に置きます。OS の `%TEMP%` を使う場合も、それを永続ストレージとして扱わず、アプリケーション固有の一意な作業ディレクトリを作成して、正常終了・失敗時の削除と次回起動時の残骸回収を設計します。

## 同時実行と安全な回収

- 各プロセスまたは作業単位の所有領域を識別し、PID と時刻だけでプロセスの生存を推定しません。
- 同時実行で容量上限を超えないよう、ファイル作成前に予約を確保し、失敗時は予約を解放します。
- 使用中のファイルは lease、ハンドル、ロックなどで保護します。期限経過だけを根拠に、利用中のファイルを強制削除しません。
- 回収対象の所有権を確認できない場合は触れず、診断可能な記録を残します。
- 起動時と作業終了時の回収を組み合わせ、突然の終了で残ったファイルを後続起動時に回収します。
- ファイルやディレクトリのパスを固定ルート配下に閉じ込め、シンボリックリンクなどによる意図しない範囲への削除を避けます。

## 検証項目

Temp 機能を変更する場合は、対象のリスクに応じて次の動作を検証します。

1. 件数・容量・単一ファイル上限に達したときの拒否または古い未使用データの回収。
2. 同時プロセスが容量予約を競合させても全体上限を超えないこと。
3. lease 中のデータは期限切れ・明示削除・容量確保時に消えないこと。
4. 入力超過、キャンセル、書き込み失敗で予約と未完成ファイルが残らないこと。
5. 終了済み owner の残骸は回収され、生存中またはロック中の owner は維持されること。
6. 削除権限がない、またはファイルがロックされている場合に、安全に失敗し次回回収へ残せること。

この節の検証項目は将来の実装向け推奨です。調査した Temp 実装自体のテスト結果を、この文書の根拠として扱っていません。
