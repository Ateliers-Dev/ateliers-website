# Windows ローカル実行記録と監査データ

> 作成日: 2026-11-23
> 更新日: 2026-11-23
> 作成者: Codex

## 目的

将来、AI 協働の実行記録や成果を分析・改善・監査に活用できるデータ基盤を目指します。このページは必要なデータの性質と管理上の要件を定めます。データベースの採用やアクセス構成を決めるものではありません。

## 記録の種類を分ける

| 種類 | 主な目的 | 保持・運用 |
|---|---|---|
| 診断ログ | 障害調査、処理の状態把握 | サイズ・世代数・期間でローテーションし、古いものを削除する。本文や機密情報を避ける。 |
| 分析用の実行イベント | 一つの AI/自動処理の開始、実行中イベント、成果、終了状態を分析する | 識別子と時刻を使って実行を追跡する。記録の欠落や部分完了を表現し、保持期間と出力範囲を定める。 |
| 監査証跡 | 重要操作や権限判断を後から説明・検証する | 分析用イベントより強い完全性・アクセス制御が必要かを明示し、保持期間、削除条件、検証方法を定める。ローカル保存だけで改ざん不能・非否認性が得られるとはみなさない。 |

分析用イベントを保存しただけで監査要件を満たすとは限りません。監査の要件が定まるまでは、各記録の保証レベルと用途を明記し、分析用データを監査証跡として保証しているかのように扱いません。監査上の完全性や法的要件が必要な場合は、脅威モデル、保護境界、外部保管や署名などを別途設計します。

## 将来の記録契約

将来の記録形式は、保存実装から独立して扱える契約を目指します。必要性とプライバシーを確認しながら、次の項目を設計時に定めます。

- 実行 ID、イベント ID、親子実行や相関の ID
- 実行の開始・終了状態。正常完了、失敗、中断などの終端状態と、終端記録がない場合の未完了・状態不明の扱い
- 実行内の順序番号または同等の順序情報。欠番、重複、順不同を検出・表現する方法
- 発生時刻、記録時刻、取り込み時刻の意味と時刻源
- 実行主体、使用したエージェントやツールの識別情報
- 操作種別、状態遷移、結果、失敗分類
- 成果物や証跡への参照、内容のハッシュなど整合性確認に使う情報
- 書き込みが「受け付けられた」「キューに積まれた」「永続化された」のどの時点で成功と応答されるか。保存失敗や未確認状態を呼び出し側へどう伝えるか
- 記録スキーマのバージョン、生成元のバージョン
- データ分類、機密性、保持期限や削除状態

終端状態は実行の完了を判断する根拠として明示します。終端記録が欠けている実行は、正常完了ではなく未完了または状態不明として扱います。順序情報に欠番がある場合や、永続化確認が得られない場合も、その不確実性を後続の分析・監査利用者が判別できるようにします。具体的なイベント形式、順序付け、永続化保証の強さはストアと脅威モデルを決める段階で選定し、今は固定しません。

イベント ID やハッシュだけでは、同一の信頼境界にある保存先を記録者と同じ権限で書き換えられる場合の改ざんを検出できないことがあります。検証可能な監査証跡が必要なら、鍵の保管場所、署名または連鎖の検証主体、外部の信頼できる保管先など、書き換え対象と独立した保護境界を設計します。実装前に保証できる範囲と検証手順を定めます。

必要以上にプロンプト、会話本文、資格情報、個人情報を蓄積しません。本文を保存する場合は利用目的、同意・権限、マスキング、保存期間、削除とエクスポート、暗号化の要件を決めます。

## SQLite とアクセス方式は未決定

将来 SQLite をローカル永続ストアに使う可能性を見据えますが、この段階でスキーマや運用仕様を決めません。次の両案は検討候補に留めます。

- MCP が SQLite を直接利用する。
- MCP がローカル API を介して SQLite を利用する。

どちらも採用決定ではありません。利用者の導入手順、認証・アクセス制御、同時実行、バックアップ、更新配布、将来の別ストアへの移行などを比較して、別途設計判断を行います。データ利用側をファイルパスや特定 DB の内部形式に直接依存させない契約を検討しつつ、抽象化の方式自体も現時点で固定しません。WAL などのジャーナル方式を選ぶ場合は、読み書きの同時実行条件と、関連ファイルを含む一貫したバックアップ方法も確認します。

データ形式やスキーマを採用するときは、バージョン管理、互換性、移行と復旧の方針を定めます。[作成・更新・削除と移行](./lifecycle.md)を参照してください。
