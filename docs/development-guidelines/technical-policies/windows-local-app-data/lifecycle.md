# Windows ローカルデータの作成・更新・削除

> 作成日: 2026-11-23
> 更新日: 2026-11-23
> 作成者: Codex

## 分類ごとのライフサイクル

保存データごとに、所有する機能、作成・更新の単位、保持期間、削除条件、復旧方法を定めます。アプリケーションの終了や通常の更新だけを理由に永続データを消しません。

| 種別 | 作成・更新 | 削除・保持 |
|---|---|---|
| 設定 | サイズと形式を検証し、一時ファイルへ完全に書いてから置換する。 | 初期化など利用者の明示操作で扱う。 |
| 永続データ | 対象形式が提供する整合性のある方法で更新する。 | 製品の保持方針、利用者の明示操作、または計画された移行で扱う。 |
| 診断ログ | サイズ・世代数・保持期間を定め、古いものをローテーションする。 | 診断目的の保持期間後に削除する。 |
| 実行記録・監査証跡 | [実行記録と監査データ](./records-and-audit.md)に定める記録契約と保証レベルを適用する。 | 通常ログのローテーション対象にせず、期限・利用者の権利・製品方針に沿って個別に扱う。 |
| キャッシュ | 再生成に必要な元データと分離し、キャッシュ単位で更新する。 | 再生成を確認してから上限・期限で削除する。 |
| 一時データ | 作業単位で隔離し、未完成データと確定済みデータを区別する。 | 作業終了・失敗・期限切れ時に回収する。使用中のものは保護する。 |

## データごとのバックアップと復元計画

各データ分類について、実装時に次の判断を記録します。

- データが正本か、元データから安全に再生成できるか。
- バックアップや利用者向けエクスポートを提供するか。提供しない場合、その理由とデータ損失時の影響は何か。
- バックアップの頻度、世代・保持期間、保存場所、アクセス保護をどうするか。必要な場合は許容できるデータ損失量と復旧時間も定める。
- バックアップの一貫性をどの方法で保ち、破損や古い形式をどう検出するか。
- 復元後に、形式・スキーマの互換性、整合性、アプリケーションからの読み出しをどう確認するか。
- 新しい端末への移行で、どのデータを持ち運び、何を再生成し、利用者にどの手順や状態表示を提供するか。

`%LOCALAPPDATA%` は端末固有の保存領域であり、端末交換やユーザープロファイル消失時のバックアップ・復元・移行を自動的に保証しません。Windows のアプリ復元機能を利用する場合も、アプリの種類や配置先などの条件を確認し、必要なアプリ状態が実際に復元されるか検証します。アプリのインストール復元だけでアプリ固有データが戻ると仮定しません。

SQLite を採用する場合、稼働中データベースの単一ファイルを単純コピーする方法を既定にしません。SQLite が提供する Online Backup API など、採用したジャーナル方式や運用条件に合う一貫した取得方法を選び、別領域への復元、整合性確認、アプリケーションからの読み出しまで検証します。具体的な方法は SQLite を採用する段階で決めます。

## ファイルの安全な更新

単一ファイルでは、対象と同じボリューム上の一時ファイルに完全な内容を書き、検証後に置換します。中断や失敗では一時ファイルを可能な範囲で回収し、既存の有効なデータを保ちます。置換の原子性や耐久性は採用する Windows/.NET API の契約を確認し、その保証を超えて説明しません。

読み込み時には許容サイズと形式を検証します。破損を検知したとき空の値で元ファイルを上書きせず、復旧可能な元データを保護し、利用者へ扱いを知らせます。

## 削除、初期化、アンインストール

- キャッシュの消去、設定の初期化、すべての利用者データの削除を別の操作として説明します。
- 永続データの削除前に対象と影響を示し、必要に応じてエクスポートやバックアップを提供します。
- アップデーターは管理対象のインストールファイルだけを更新し、ユーザーデータルートを無差別に再帰削除しません。
- アンインストール時にデータを保持または削除する動作と、後から削除する方法を利用者向けに明記します。
- 削除に失敗した場合は成功と報告せず、残ったデータと再試行方法を案内します。

## 保存先・形式・スキーマの互換性と移行

保存先、ファイル形式、将来のデータベーススキーマを変更するときは、互換性を変更計画の一部として扱います。新旧バージョンが同じデータを開く可能性、ダウングレード時の読み書き、データ破損時の復旧、バックアップ互換性を確認します。アプリケーションのバージョン番号とデータ形式・スキーマのバージョンを同一視しません。

自動移行を行う場合は、移行前の検証と必要なバックアップ、段階的な書き込み、完了状態の記録、再起動後の安全な再試行、失敗時の復旧方法を設計します。移行完了を確認する前に元データを削除しません。移行元・移行先・互換性のあるバージョン範囲を文書化し、利用者が移行状況を確認できるようにします。

旧形式を読み取れる互換期間を設けるか、変換ツール・エクスポート形式を提供するかは、データの重要度と利用者要件に応じて決めます。既存実装で旧保存先の自動移動・削除をしない例があっても、今後の標準移行方針をそれに固定しません。

## 診断

読み込み、書き込み、移行、削除の失敗は、操作名、結果、例外種別など復旧に必要な範囲で診断します。本文、資格情報、個人データを通常ログへ出さないようにします。監査目的で必要な操作記録は通常ログと分離し、[実行記録と監査データ](./records-and-audit.md)に従います。

[一時データと容量管理](./temporary-data.md)は短命データに追加する要件を定めます。
