# 記入例：Markdown 変換 CLI の MVP

> 以下はテンプレートの使い方を示す架空の例です。実在するプロジェクトの仕様ではありません。

## Must（必須項目）

### 1. 目的・成果物

- **目的・解決する課題：** 小さな Markdown 文書をプレーンテキストへ変換し、手作業で書式記号を取り除く手間を減らす。
- **対象利用者：** ローカルで文書を処理する開発者。
- **成果物：** UTF-8 の Markdown ファイルを受け取り、見出しと箇条書きを簡易変換して標準出力へ出す CLI。

### 2. 開発範囲・対象外

- **今回の範囲：** 見出し記号と箇条書き記号の除去、空行の維持、入力ファイル指定、標準出力と終了コード。
- **今回の対象外：** Markdown 全仕様への対応、HTML 変換、画像・表・リンクの整形、ディレクトリ一括処理。

### 3. 完了条件

- [ ] 指定した UTF-8 ファイルを変換し、定義した書式記号を除いたテキストを出力する。
- [ ] 不在ファイルや不正な引数では、標準エラーに説明を出し、0以外で終了する。
- [ ] 主要な正常系とエラー系の自動テストが通る。
- [ ] README に実行方法と対応範囲を記載する。

### 4. 開発段階

| 段階 | 作業・成果 | 次へ進む条件 |
|---|---|---|
| 1. 仕様の固定 | 対応する記号、入力・出力、エラー動作を短い仕様メモに記録 | 変換例と対象外が確認できる |
| 2. MVP 実装 | CLI と自動テストを実装 | Must の完了条件をテストと手動確認で満たす |
| 3. 受け入れ | README とサンプルを確認し、既知の制約を記録 | 受け入れ判断者が完了条件と検証結果を確認する |

### 5. 検証方法

- **完了条件の確認方法：** 自動テストで出力文字列と終了コードを確認し、サンプルファイルでも実行する。
- **レビュー・テスト：** 変換ロジック、引数、エラー時の出力をレビューする。表やリンク対応の提案は範囲外の改善案として扱う。
- **失敗や未達の場合の記録・対応：** 入力、期待値、実際の出力、原因、修正内容をテストやレビュー記録に残し、範囲変更が必要なら計画を更新する。

### 6. 変更管理

- **変更を記録する場所・方法：** リポジトリの Issue と Pull Request に記録する。
- **範囲・完了条件・段階・検証への影響確認：** 新しい Markdown 機能を追加する提案は、MVP の範囲と完了条件への影響を確認してから扱う。
- **判断・承認者（プロジェクトの権限に応じて）：** リポジトリの変更権限を持つメンテナーが計画変更を判断する。

## Optional（任意項目）

### 1. 要求仕様書

- **参照先または要約：** この計画の Must 項目と変換例を要求の原本とする。別の仕様書は作成しない。

### 2. アーキテクチャ・技術選定

- **構成・選定と理由：** 依存を増やさない小さな単一実行ファイルとし、変換ロジックを CLI 入出力から分離する。

### 3. マイルストーン・日程

| マイルストーン | 目標日 | 完了の目安 |
|---|---|---|
| MVP 受け入れ | 日程は未設定 | Must の完了条件をすべて確認 |

### 4. 役割・責任分担

| 役割 | 担当・責任 |
|---|---|
| 実装・レビュー | 小規模作業のため担当者が兼務可能。受け入れ判断は変更権限者が行う |

### 5. リスク・制約

- **リスク・制約：** 対応する Markdown は限定的で、複雑な書式は期待どおりに変換されない。
- **対応：** README と CLI のエラー・ヘルプで対象外を明示する。

### 6. リリース・配布計画

- **対象・方法：** MVP は開発リポジトリ内の実行方法を案内する。
- **受け入れ・公開の判断者：** メンテナーが受け入れを判断する。別途の配布は本計画の範囲外とする。

### 7. ログ・監査・復旧方針

- **記録する内容と保管先：** エラー内容を標準エラーへ出す。通常の入力内容は記録しない。
- **問題発生時の確認・復旧方法：** 再現用入力とテストを使い、修正後に該当テストを再実行する。

### 8. 既存システムとの互換性

- **対象システム・バージョン：** 開発者が利用する対応 OS とランタイム。
- **互換性の条件と確認方法：** 対応環境を README に明記し、代表環境で起動と基本変換を確認する。
