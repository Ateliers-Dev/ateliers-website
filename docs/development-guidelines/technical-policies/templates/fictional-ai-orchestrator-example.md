# 記入例：AI オーケストレーター（架空）

> これは複数段階の計画例を示すための架空のプロジェクトです。実在するプロジェクトの確定仕様、現在の実装、ロードマップを表すものではありません。

## Must（必須項目）

### 1. 目的・成果物

- **目的・解決する課題：** 小規模なコード変更について、実装と独立レビューを段階的に実行し、結果を追跡しやすくする。
- **対象利用者：** 実行内容を確認して最終判断するリポジトリのメンテナー。
- **成果物：** 入力された課題を使い、作業領域内で変更を作成し、レビュー結果と検証記録をまとめる実験用オーケストレーター。

### 2. 開発範囲・対象外

- **今回の範囲：** 1つのテスト用リポジトリ、1回の実装、独立レビュー、上限2回の修正、最終報告までのローカル実行。
- **今回の対象外：** 自動マージ、無人での本番リリース、複数リポジトリの同時実行、認証情報を伴う外部操作、無制限の再試行。

### 3. 完了条件

- [ ] 実装、レビュー、修正の各結果と、使用した計画・検証結果を実行記録から確認できる。
- [ ] レビュー指摘は、計画内の問題と範囲外の提案に分けて扱う。
- [ ] 修正回数の上限、失敗時の停止条件、実行ディレクトリの制約が守られる。
- [ ] テスト用リポジトリで正常系、レビュー指摘からの修正、上限到達、実行失敗を再現できる。
- [ ] 人間が変更差分、未解決事項、検証結果を確認して受け入れ判断できる。

### 4. 開発段階

| 段階 | 作業・成果 | 次へ進む条件 |
|---|---|---|
| 1. 実行契約の定義 | 入力、権限、作業領域、停止条件、記録項目を定義 | 安全な実験範囲と失敗時の終了動作をレビュー済み |
| 2. 最小実行フロー | 課題入力から実装結果・記録までを実装 | テスト用リポジトリで正常系の完了と失敗停止を確認 |
| 3. 独立レビュー | 別のレビュー処理で差分を確認し、指摘を分類 | 計画内の問題と範囲外の提案を区別できる |
| 4. 有界修正 | 計画内の指摘のみを最大2回修正し、再レビュー | 上限内で完了するか、上限到達として確実に停止する |
| 5. 受け入れ評価 | シナリオ検証、記録の確認、制約の整理 | 完了条件と既知の失敗が人間に提示され、受け入れ判断が可能 |

### 5. 検証方法

- **完了条件の確認方法：** テスト用リポジトリで各シナリオを実行し、状態遷移、差分、記録、停止理由を確認する。
- **レビュー・テスト：** 実装者とは独立したレビュー処理を使う。レビュー承認、段階移行、プロジェクト全体の受け入れを別々に確認する。
- **失敗や未達の場合の記録・対応：** 入力、各段階の出力、エラー、再試行数、原因、影響、復旧可否を記録する。権限逸脱や安全な継続ができない場合は停止し、人間の判断を求める。

### 6. 変更管理

- **変更を記録する場所・方法：** 計画、設計判断、実装課題、検証結果をプロジェクトリポジトリで管理する。
- **範囲・完了条件・段階・検証への影響確認：** エージェント追加、権限拡張、修正上限変更、外部操作の追加は、対象範囲とリスクを再評価し、完了条件とシナリオを更新してから実装する。
- **判断・承認者（プロジェクトの権限に応じて）：** 実験の責任者が計画変更を判断する。外部への影響や権限拡張を伴う場合は、その操作を委譲する権限を持つ人が判断する。

## Optional（任意項目・省略可能）

### 1. 要求仕様書

- **参照先または要約：** テストシナリオと実行契約をリポジトリ内の短い仕様書に記録する。

### 2. アーキテクチャ・技術選定

- **構成・選定と理由：** 実行管理、実装処理、レビュー処理、記録処理を分ける。各段階の入出力を固定し、個々の処理をテストしやすくする。

### 4. 役割・責任分担

| 役割 | 担当・責任 |
|---|---|
| 実装処理 | 計画内の変更を作成し、変更内容を報告する |
| レビュー処理 | 差分を独立して確認し、指摘と提案を分類する |
| 実験責任者 | 計画・段階の判断と、最終受け入れを行う |

### 5. リスク・制約

- **リスク・制約：** エージェントの出力が不正確な場合や、段階間の受け渡しが欠落した場合に、意図しない変更や誤った完了報告につながる。
- **対応：** 専用のテスト用リポジトリ、最小権限、固定された修正回数、独立レビュー、差分と記録の人間確認を設ける。

### 7. ログ・監査・復旧方針

- **記録する内容と保管先：** 実行識別子、段階、入力参照、差分、判定、検証結果、失敗理由をリポジトリ外の秘密情報を含めずに記録する。
- **問題発生時の確認・復旧方法：** 失敗段階で停止し、ログと差分を保持する。再実行は同じ変更を重ねないことを確認してから行い、作業領域を破棄・復元できる手順を用意する。

### 8. 既存システムとの互換性

- **対象システム・バージョン：** 実験用リポジトリの指定ブランチと、そこで使われるビルド・テスト環境。
- **互換性の条件と確認方法：** 既存の作業ツリーや未コミット変更に触れず、対象リポジトリの標準検証手順が実行できることを確認する。
