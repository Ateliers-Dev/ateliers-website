# ブランチ戦略ガイドライン

> 作成日: 2026-11-22
> 更新日: 2026-11-22
> 作成者: Codex

このガイドラインは、ブランチ戦略を一つの方式に固定せず、プロジェクトのリリース形態、品質ゲート、運用能力に合わせて選ぶための共通基準を示します。各プロジェクトは採用する方式と必要な調整を、プロジェクト計画や開発ルールで明示します。

ブランチ戦略は品質ゲートそのものを決めるものではありません。品質ゲートの共通基準は[レビュー工程と品質判定の共通方針](./review-process-guidelines.md)、プロジェクトごとの具体的なゲートはそのプロジェクトの計画・運用文書で定めます。

## 選定の観点

方式を選ぶときは、少なくとも次を確認します。

- 開発統合とリリース判定を同じ段階で行うか、別々の段階で行うか
- 本番に出す前に、候補を別の環境や承認工程で確認する必要があるか
- 同時に保守する製品バージョンや顧客別系列があるか
- CI、レビュー、デプロイ、ロールバックの仕組みが選んだ流れを支えられるか
- 長期ブランチを維持する作業量と、分岐した修正を反映し続ける負担が見合うか

## 主な方式

| 方式 | 基本的な流れ | 適する状況 | 主な注意点 |
|---|---|---|---|
| GitHub Flow | 作業ブランチから Pull Request を作成し、レビュー・必要なチェック後に `main` へ統合する | 単純な継続的開発で、統合後に速やかに公開できる | リリース前の別ゲートが必要な場合は、環境・承認・機能フラグなどを別途設計する |
| GitLab Flow（環境ブランチ型） | 作業ブランチを `main` に統合し、候補を `production` など下流の環境ブランチへ段階的に昇格する | 開発統合とリリース判定を分け、候補を固定して段階別に検証したい | 候補と昇格先の対応、昇格手順、各段階のゲートを定める必要がある |
| Git Flow | `develop`、`release/*`、`hotfix/*`、`main` など複数の役割別ブランチを使う | 定期リリースや、複数のバージョン系列を並行して保守する | ブランチと修正の取り込み先が増え、維持・マージの負担が大きくなる |
| Trunk-Based Development | 変更を短命の作業ブランチから頻繁に統合し、必要に応じて機能フラグで公開を制御する | 自動検証と小さな差分を高頻度で統合できる | 長期未統合の変更を避ける運用と、機能フラグの管理が必要 |

これらの名称には複数の運用形があります。名称だけで工程や品質水準が決まるとは扱わず、採用するブランチの役割と実際のゲートをプロジェクトごとに記録します。

## Ateliers-Dev で現在選択している方式

Ateliers-Dev では、現在の共通方式として GitLab Flow の環境ブランチ型を選択します。基本形は作業ブランチから開発品質ゲートを通過して `main` へ統合し、候補を固定したうえでリリース品質ゲートを通過した内容を `production` へ昇格する流れです。

この方式を選ぶ理由は次のとおりです。

- 開発レビュー・開発用チェックと、提供前のリリースレビュー・実環境検証を別工程に配置できる。
- `main` を開発ゲート通過済みの統合先、`production` をリリースゲート通過済みの昇格先として区別できる。
- 検証対象をコミット SHA で固定し、`main` の後続変更を候補へ混ぜずに開発を続けられる。
- リリースごとの長期 `release/*` ブランチを通常は作らず、正式リリースの履歴を `production` 上のコミットに付けるタグで記録できる。
- 複数版の並行保守が必要になった場合は、その必要性と修正の取り込み方を確認して保守ブランチを追加できる。

`main` は開発品質ゲートを通過した変更の統合先であり、リリース品質ゲート通過前の変更を含むことがあります。`production` はリリース品質ゲート通過済みの内容を受け取ります。正式リリースのタグは、実際にリリースする `production` のコミットを指します。両ブランチへの統合は Pull Request を通じて行い、直接マージしません。

この選択は GitHub Flow など他の方式を禁止するものではありません。プロジェクトのリリース方式やリスクが異なり、別方式の方が適合する場合は、その理由とブランチ・ゲート・リリース・復旧の対応をプロジェクト計画に記録して選択できます。

## 方式を追加・変更するときの記録形式

新しい方式やプロジェクト独自の変形を選択する場合は、次の内容を記録します。

1. 方式名と採用する変形
2. ブランチごとの役割、作成元、統合先、保護条件
3. 開発レビュー、CI、結合・実環境検証、リリースレビューの実施点
4. 候補の固定方法と、検証証跡を再利用・再実施する条件
5. リリースタグ・成果物・デプロイの対応
6. 障害時の停止・復旧・修正の取り込み方法
7. 複数バージョンを保守する場合の期間、責任者、終了条件
