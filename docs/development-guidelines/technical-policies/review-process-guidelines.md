# レビュー工程と品質判定の共通設計

> 作成日: 2026-11-22
> 更新日: 2026-11-22
> 作成者: Codex

> 本書は設計提案です。承認・反映されるまでは、既存のガイドラインやプロジェクト規則を置き換えません。

この文書は、Ateliers-Dev の開発レビュー、設計レビュー、検証レビュー、リリースレビュー、Review Planning、Quality Gate の責務と判定境界の設計案を提示します。各プロジェクトの要求、実施するレビュー、記録先は、開発リポジトリの計画と運用規則を原本として決めます。

[品質ガイドライン](./quality-guidelines.md) と [開発プロセスガイドライン](./development-process-guidelines.md) を補完します。PoC、MVP、Product などの分類や、提供段階ごとの品質水準を置き換えるものではありません。

## 目的と基本原則

レビューが終わらない原因となる、開発対象と外部依存の責任混同、設計・実装・検証の証拠混同、技術的重大度と工程判定の混同を防ぎます。

- 開発対象のコードが要求を実装し、外部依存の公開契約に従い、安全な失敗処理を行うことは開発側の責務です。
- 外部 CLI、ライブラリ、OS、実行基盤の内部品質は原則として提供元の責務です。公開仕様に従った正常動作を開発レビューの前提にできます。
- 依存先の呼び出し方、バージョン・設定の選択、入力検証、権限、結果処理、要求された fail-closed は開発対象のレビュー範囲です。
- 自作コードと依存先の結合動作は、計画で必要としたときに適切な環境で検証します。単体テストやコード確認を結合動作の証拠として扱いません。
- 環境で依存先を起動できない事実は、そのまま開発対象の欠陥とはしません。未実施・阻害された検証として記録し、今回の完了条件または重大リスクに関係するときだけ、その影響を工程判定に反映します。
- 指摘の技術的重大度と、現在の工程を止めるかどうかを分けます。範囲外の改善提案をレビュー中に完了条件へ追加しません。
- レビュー、段階移行、受け入れ、公開・リリースは別の判断です。レビューや Gate の結果だけで統合・公開を自動承認しません。

## 工程と役割

各工程は機能上の責務です。小さな変更では、一つの人または AI が順番に複数の機能を担っても構いません。必要性がない限り、個別 Skill や独立エージェントを工程ごとに新設することは求めません。実装者と独立レビュー担当の分離が必要な場合は、計画またはリポジトリ規則で定めます。

| 工程 | 主な責務 | 判断しないこと | 主な出力 |
|---|---|---|---|
| Review Planning | 目的、範囲、品質条件、必要なレビューと検証、工程ごとの完了条件をレビュー開始前に明示する | 実装の正否、証拠のない品質達成 | Review Plan |
| 開発レビュー | 差分の実装、要件適合、依存契約の使い方、エラー処理、変更範囲内の欠陥を評価する | 外部依存の内部品質、提供・リリース可否 | Code Findings |
| 設計レビュー | 要求、設計、責務境界、安全モデル、段階に応じた設計の整合性を評価する | 未実装・未検証の設計意図を実績とすること、範囲外の詳細設計を強制すること | Design Findings |
| 検証レビュー | 計画した検証の方法、対象、実行結果、証跡が完了条件を裏付けるかを評価する | 未実行試験の成功推定、開発対象と無関係な環境障害のコード欠陥扱い | Verification Findings |
| Quality Gate | 合意済み条件と工程結果を照合し、次工程への進行状態を返す | 技術指摘の書き換え、計画外の品質要求の追加、マージ・リリースの最終承認 | Gate Decision |
| リリースレビュー | 提供対象と予定環境に照らし、リリース条件、結合証跡、配布・運用準備、既知の制約を評価する | 外部依存内部の包括的監査、権限者に代わる提供決定 | Release Readiness Report |
| 権限を持つ判断者 | 条件変更、残余リスク受容、段階移行、受け入れ、公開・リリースを決める | 不在の証拠を存在したものとして扱うこと | 人による判断記録 |

## Review Planning

Review Planning は、レビュー指摘が作業範囲を際限なく広げないよう、レビュー開始前に今回の判定条件を固定します。小規模作業では計画や PR の記載に短くまとめられます。

計画には必要な範囲で次を記録します。

- 成果物の目的・段階、対象利用者・環境、今回の成功条件
- 今回の範囲と対象外、要求・完了条件への参照
- 実行リスク、変更できない安全上の最低条件
- 実施するレビュー工程と、実施しない工程
- 完了条件ごとの検証方法、必要な証跡、対象環境・依存バージョン
- 外部依存について、公開契約を前提にする範囲と結合確認が必要な範囲
- 判定者、必要な人の承認、結果を記録する場所

### 計画が不足・変更された場合

目的、完了条件、実行リスクのいずれかが判定に必要なのに不明な場合、Planning は推測で品質水準を決めません。必要な情報を確認し、決まるまで影響を受けないコード確認や事実整理だけを限定して進められます。重要な条件が欠けたまま、受け入れ・段階移行・リリースの Gate を通過させません。

レビュー中に新しい要求やリスクが見つかった場合、レビュー担当は事実・影響・根拠を報告します。人が変更を判断するまでは元の計画で評価し、変更が承認されたら範囲、完了条件、必要な再レビューを記録して更新します。レビューの反復回数だけを理由に新しい試験や設計要求を追加しません。反復しても結論が収束しない場合は、差分全体と計画を見直し、人の判断へ戻します。

## レビュー別の実施条件と完了条件

| 工程 | 実施する条件 | 完了条件 |
|---|---|---|
| 開発レビュー | コード、構成、テスト、または実装成果物が変わり、計画がレビューを要求するとき。リスクや変更内容に応じて範囲を選ぶ | 対象差分・要求・完了条件に照らした指摘を記録し、重大度、根拠、修正要否を区別する。未確認事項とレビュー対象外を示す |
| 設計レビュー | 新規設計、責務・境界・外部契約・安全条件の変更があり、計画上必要なとき | 要求から設計への追跡、責務の割当て、重大な矛盾・不足を示す。今回の段階で必要な詳細度を満たすかを記録する |
| 検証レビュー | 完了条件にテスト・実験・手動確認などの検証が含まれるとき | 各対象条件について、検証方法と結果、証跡の範囲、未実施・失敗・環境阻害を分類し、証拠が支える結論の上限を示す |
| Quality Gate | 段階移行、受け入れ、またはリリース前に、計画で Gate を設けたとき | 事前に定めた条件と結果を照合し、次工程の状態・理由・条件・判断者を記録する |
| リリースレビュー | 配布、外部公開、または運用環境への導入を予定し、提供判定を必要とするとき | 対象版・対象者・環境、必要な結合証跡、配布・運用・復旧条件、既知の制約を評価し、人が提供判断を行える状態にする |

工程を適用しない場合、必須工程として計画されていなければ、不要な成果物を作る必要はありません。計画上必須の工程を省く場合は、計画変更の判断を記録します。

## 外部依存と検証境界

| 対象 | 開発側が確認すること | 原則として開発レビューで保証しないこと |
|---|---|---|
| 自作コードとアダプター | 公開 API・CLI 契約に沿う呼び出し、引数・設定、バージョン条件、入力・出力処理、権限、タイムアウト、エラー伝達 | 依存先の非公開内部実装全体の正しさ |
| 依存障害時の自作コード | 要求された安全な停止、結果を成功扱いしないこと、意図しない特権実行・安全境界の迂回がないこと | 依存先があらゆる環境・条件で常に稼働する保証 |
| 外部 CLI・ライブラリ・OS・実行基盤との結合 | 計画で重要な場合、対象の組み合わせと環境での実行結果を適切な検証工程で確認する | 特定環境の利用不能だけを理由に、開発対象のコード欠陥と断定すること |
| 公開済みの依存不具合 | 対象バージョンへの影響が証拠で確認でき、開発対象に回避・制約を設ける要求がある場合に評価する | 関連性の根拠なく、すべての依存内部品質を監査すること |

外部依存が公開仕様どおりに働くと仮定した静的・単体レベルの開発レビューは可能です。結合試験が環境制約で実行できなかった場合は、対象環境、試行内容、観測された失敗、未実行の試験群、再開条件を記録します。コード上確認した設定を、実環境での成功証跡に言い換えません。

実結合確認を Gate の必須条件とするかは、Review Planning が完了条件とリスクから事前に決めます。条件に含めていない結合試験を、レビュー中に後付けして自動的な保留理由にしません。未確認の挙動が明示要件または重大なリスクに関係し、その影響を既存のコード・テスト・仕様の証拠から評価できない場合は、理由と必要な証拠を特定して Gate を保留できます。要件にも重大リスクにも関係しない未確認は、範囲を明示した残課題として記録します。

## 指摘と Quality Gate の判定

技術的重大度と工程への影響を別々に記録します。P0–P3 等の重大度は既存プロジェクト規則に従い、この共通文書は新しい重大度体系を導入しません。

| Gate 状態 | 意味 |
|---|---|
| 通過 | 今回の計画で定めた当該 Gate の条件が満たされている |
| 条件付き通過 | 条件、残るリスク、責任者、期限または再確認点が明確で、権限を持つ判断者が継続を認めた |
| 保留 | 必須条件の未達、根拠の不足、または未軽減の重大リスクにより次工程の判断ができない |
| 計画見直し | 目的・要求・環境・リスクなど計画前提が変化し、現在の条件では有効な判定ができない |

Gate は技術指摘を消したり、重大度を下げたりしません。範囲外の提案は、今回の必須修正にせず、必要に応じて後続課題候補として記録します。条件付き通過や残余リスクの受容は、権限を持つ人の判断を要します。AI やレビュー担当が単独で安全条件を緩和しません。Gate の通過はマージやリリースの承認ではありません。

## リリースレビュー

リリースレビューは、開発レビューの再実行ではなく、計画された提供対象に対する受け入れ準備の評価です。提供段階に応じて、次のうち必要な項目だけを対象とします。

- 対象バージョン、利用者・環境、変更内容、既知の制約
- 提供判定で必須とした受け入れ条件と、対象版に結びつく証跡
- 外部依存を含む実動作の確認が必要な場合、その環境・バージョンでの結果
- 配布物、導入・更新手順、互換性、運用・監視、停止・復旧方法
- 未解決指摘、受け入れた条件、残余リスク、利用者への説明
- リリース判断者と、提供・延期・範囲縮小・差し戻しの判断記録

PoC や内部 MVP に製品運用の全項目を一律に要求しません。正式公開や継続運用では、そこで合意された利用条件とリスクに見合う項目を計画します。外部依存の内部品質は提供元の責務を基本とし、リリースレビューも依存全体の監査を目的としません。依存先の対象バージョンで再現した不具合が提供条件を脅かすときは、影響を記録し、回避策・提供条件・延期を権限者が判断できるようにします。

## 証跡と報告契約

レビュー結果は、人が事実、評価、判断を区別でき、必要な再確認ができる形で返します。内部受け渡しは既存の仕組みに合わせ、必ずしも別ファイルや新しいデータ形式を導入しません。

各報告に必要な情報は次のとおりです。

1. **対象**：リポジトリ、PR または成果物、対象コミット／版、レビュー工程、計画・完了条件。
2. **範囲**：確認した資料・差分、実施した確認、対象外。
3. **所見**：一意な識別子、事実と根拠、影響・理由、技術的重大度、Gate への影響、必要な対応時期。
4. **証拠状態**：設計済み・実装済み・検証済みを区別し、試験は成功・失敗・未実施・環境阻害を区別する。
5. **外部依存**：依存名・版、公開契約を前提とした範囲、実結合確認の範囲、未確認事項と環境条件。
6. **結論**：担当工程の結論、残る不確実性、再開に必要な条件。報告者がリリース判定者でない場合、その権限を越えた承認表現をしない。
7. **記録先**：報告書または PR などの原本を明示し、同一内容を複数箇所に重複投稿しない。

指摘がない場合も、対象コミット、評価した範囲、確認済み証拠、未確認事項、工程上の結論を簡潔に記載します。作者・CI からの申告と、報告者が直接確認した事実を区別します。

### 報告と投稿の責務案

| 方式 | 利点 | 留意点 |
|---|---|---|
| Reviewer が直接投稿 | 受け渡しの手順が少ない | 読み取り専用の独立性と投稿権限が混ざり、重複・再試行時の管理が Reviewer に集中する |
| Reviewer が報告を返し、記録担当が投稿 | 技術評価と外部への記録権限を分け、投稿状況を一箇所で管理しやすい | 記録担当への受け渡しと投稿結果の確認が必要 |
| Orchestrator が集約して投稿 | 複数工程の結果を一貫した書式でまとめられる | Orchestrator がない運用にも適用できるよう、固有実装を共通方針にしない |

本設計案では、役割として「レビュー結果の作成」と「外部記録の実行」を分け、実際の担当者やエージェント構成は運用に応じて決める案を採ります。独立レビュー担当が読み取り専用である場合、GitHub への投稿を担当する必要はありません。結果を権限のある記録担当に引き渡します。投稿は依頼と権限の範囲内で行い、権限不足、投稿失敗、結果不明の場合は成功したものとして扱わず、既存の記録先と重複しない方法で状態を報告します。投稿や記録は人の承認、マージ、公開の代わりにはなりません。

## PR #127 事例への適用

PR #127 の記録では、Codex sandbox 用の起動設定、引数、環境変数のコード・単体テスト、Windows・Ubuntu CI は確認されています。一方、記録された Windows 環境では sandbox backend が起動せず、実 sandbox 内の試験群は未実行でした。

本設計では、開発レビューは Orchestrator 自身の呼び出し設定と失敗時の fail-closed を評価し、backend 起動拒否そのものをコード欠陥としません。検証レビューは CI と単体テストの証拠範囲を示し、sandbox 内の結合結果を未確認と記録します。実 sandbox 試験を当該 Gate の必須条件として計画していたか、未確認が完了条件または重大リスクにどう関係するかを Quality Gate が確認します。実環境での提供可否は、別途必要なリリースレビューと権限者の判断に属します。

この説明は事例に設計を当てはめたものであり、PR #127 の現在のレビュー、マージ判断、運用変更ではありません。

## 既存課題との対応と後続作業

この設計文書の承認後に、Skill や自動化の実装を別の作業として計画します。実装方法や担当エージェントの数は、設計文書だけでは決めません。

| 既存課題 | 本設計で対応する論点 | 設計確定後に整理する作業 |
|---|---|---|
| Issue #23：AIレビューのスコープと段階別判定基準 | 計画で範囲・完了条件・安全下限を固定し、工程別レビュー、指摘の扱い、計画変更・反復停止を定義 | Reviewer の責務・出力と回帰ケースを本設計に合わせる |
| Issue #24：レビュー前の品質プロファイル判断と Quality Gate 伝達 | Review Planning の入力・出力、Quality Gate の役割、重大度と工程判定の分離、人の承認境界を定義 | 品質条件の受け渡し方式、未指定・矛盾時の運用を実装対象として決める |
| Issue #22：GitHub PR・Issue コメント運用 | 証跡・報告契約、読み取り専用 Reviewer から記録担当への受け渡し、権限・重複投稿・失敗状態を定義 | レポートの具体的書式、Publisher の投稿権限と重複防止を決める |

この PR では Issue を更新・クローズせず、Skill の追加・改修、回帰テスト、Orchestrator や PR #127 の変更も行いません。設計を人が確定した後に、既存 Issue の受け入れ条件との対応を確認し、実装の範囲・順序・完了条件を計画します。
