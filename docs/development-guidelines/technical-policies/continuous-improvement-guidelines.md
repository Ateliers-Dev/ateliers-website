# 継続的改善ガイドライン

> 作成日: 2026-11-24
> 更新日: 2026-11-24
> 作成者: Codex

## 目的と適用範囲

このガイドラインは、Ateliers の活動で得た問題・知見・改善結果を、必要なときに再評価し再利用できる形で残すための枠組みを定めます。将来はドキュメントに加え、Skill、AGENTS.md、開発プロセスなどにも適用できます。

今回の具体的な運用対象は、文書作成と報告品質に限ります。この文書だけで、他の対象への定期点検、新しい承認工程、改善の実施義務を定めるものではありません。対象ごとの既存方針や権限を優先します。

改善は、記録や文書を増やすこと自体ではなく、事実をもとに役立つ変更を行い、その結果を正確に伝えることを目的とします。

## 記録する概念

改善記録では、次の3つを独立した概念として扱います。

| 概念 | 記録する内容 | 例 |
| --- | --- | --- |
| **事象（Observation）** | 観測した事実、発生条件、影響、事実と推測の区別 | 読者が情報を見つけられない、判断に必要な情報が不足している |
| **改善手順・検討（Improvement Process）** | 調査、原因や選択肢の検討、対象範囲、採用理由、レビュー方法 | 読者別に粒度を設計し、既存分類との関係を確認する |
| **実施した対処・結果（Action / Outcome）** | 実施した変更、関連する事象・検討、検証根拠、結果、制約 | ガイドライン更新、レビューでの修正、未実施の検証 |

各概念には安定した ID を付け、リンクや ID 参照で関連付けます。1つの事象に複数の検討や対処が結び付くことも、1つの検討・対処が複数の事象に関係することもあります。記録数を 1:1:1 に揃えず、対応関係を明示してください。該当する記録がまだない場合は、無理に作らず未記録であることを示します。

記録は、既存の文書へ見出しを追加する方法でも、まとまりのある報告書にする方法でも構いません。独立ページにするのは、後から探す・参照する価値がある場合に限り、関連情報の過剰な分割は避けます。

## 改善の流れ

1. **問題や新しい知見を見つける。** 不便、誤解、矛盾、失敗、想定外の結果、または有効だった工夫を契機にします。定期点検の日程だけを理由に改善課題を作る必要はありません。
2. **事実を記録する。** いつ、どこで、誰がどの情報や動作を確認したか、影響と証拠を記します。観測事実、報告された内容、評価、仮説を区別します。
3. **改善案を検討する。** 原因や複数の可能性を検討し、目的、対象範囲、対象外、期待する変化、主なリスクを定めます。既存の方針や分類で扱えるか、変更に見合う価値があるかも確認します。
4. **対処を実施する。** 採用した変更と判断の根拠を記録します。採用しなかった案や延期した案は、再利用に役立つ場合に限って理由を残します。
5. **検証する。** 対処が意図した内容になっているか、対象となる完了条件やレビュー観点に照らして確認します。未実施、失敗、環境上の阻害を成功として扱いません。
6. **結果を記録する。** 改善前後で何が変わったか、確認した根拠、残る影響、未検証事項を記します。期待した効果と観測できた効果を分けます。
7. **必要時に再評価する。** 同じ事象の再発、新しい証拠、利用者の反応、関連方針の変更などがあれば記録を読み直し、維持・修正・置換・終了を判断します。見直しを機械的な周期義務にしません。

結果が期待に届かなかった場合、実施しなかった場合、または検証できなかった場合も、分かったことと制約を記録します。失敗を正確に残すことは、次の人が同じ案を無条件に繰り返さないための成果です。

## 改善前後と証拠

改善記録には、規模に応じて次を含めます。

- 改善前の状態と、誰にどのような影響があったか。
- 対処後に変えたことと、変えなかったこと。
- 検証の対象、方法、観測結果、証拠の範囲。
- 実施していない確認、判断できない点、残るリスク。
- 次に再評価するきっかけ（既知なら）。

「改善した」「解決した」と結論する場合は、その範囲を支える証拠を示します。文書や仕組みを変更したことだけで、実運用での効果まで確認済みとはしません。

## Issue と永続的な知識

GitHub Issue は担当、優先度、進捗、完了を管理するタスクです。Issue がクローズされても、再利用する価値のある観察、判断、結果は Docs の原本に残します。Issue には永続的な知識記録へのリンクを置けますが、Docs に Issue の全履歴を重複転記する必要はありません。

個別の作業報告が一時的な進捗共有に留まり、再利用する知識や判断を含まない場合は、別の恒久文書を作る必要はありません。記録の配置は[Website Management](../website-management.md)と既存のリポジトリ方針に従います。

## 文書作成・報告品質への今回の適用

文書作成や報告の問題では、読者が必要な判断をできるか、実装・検証に必要な詳細を失っていないか、概要と原本の関係が明らかかを確認します。改善前後を比較するときは、短くなったかどうかだけでなく、読者が必要な情報へ到達できるかを見ます。

今回の事例と適用範囲は[管理者向け文書・報告の情報粒度改善](../continuous-improvement/documentation-and-reporting-granularity-2026.md)に記録しています。事例を使うときも、そこで明記された検証範囲を超えて有効性を推定しません。
