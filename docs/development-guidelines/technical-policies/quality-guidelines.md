# 品質ガイドライン

> 作成日: 2026-11-18
> 更新日: 2026-11-18
> 作成者: Yuu503

この文書は、Ateliers-Dev の複数のプロジェクトで、成果物の目的に合った品質を定め、開発・レビュー・受け入れの判断に使うための共通指針です。プロジェクト固有の要求、設計、運用手順の原本は、それぞれの開発リポジトリで管理してください。

## 基本方針

**品質とは、単純な高さではなく、目的・要求・制約に対して適切であることです。**

すべての成果物に同じ品質水準を求めるのではなく、何を実現・検証するのか、誰にどの段階で提供するのか、失敗した場合にどのような影響があるのかを踏まえて、必要な品質を定めます。

以下に示す分類別の記述は、水準を考えるための目安です。各項目を一律の義務や合否条件として扱うものではありません。プロジェクトで合意した要求と完了条件を判定基準とし、品質水準を変更する場合は、その理由と影響を計画に反映します。

## 成果物の目的

成果物は、主に何を達成するために作るかという観点で、次の5つに分類できます。分類は品質の優劣や、開発の順番を表すものではありません。特に PoC と MVP は目的が異なり、どちらかが一律に上位という関係ではありません。

| 分類 | 主な目的 | 完了の判断例 |
|---|---|---|
| **Sample** | 仕組みや使い方を理解・説明する | 説明したい使い方や概念を確認できる |
| **Experiment** | 個別の技術・仮説・動作を検証する | 対象の問いに対する結果と条件が分かる |
| **PoC** | 構想や方式の実現可能性を検証する | 重要な前提を試し、実現可能性を判断できる |
| **MVP** | 限定した主要価値を実動作で実証する | 対象範囲で主要な価値を評価できる |
| **Product** | 機能を継続的に提供・保守する | 合意した機能と品質を提供し、運用・保守できる |

分類に迷った場合は、作り方や規模ではなく、今回の成果物で主に何を明らかにしたいか、または何を提供したいかで選びます。

| 判断したいこと | 分類 |
|---|---|
| API の使い方を説明したい | Sample |
| API の動作を検証したい | Experiment |
| 複数技術を組み合わせた構想の成立を確認したい | PoC |
| 主要機能を動かし、製品価値を評価したい | MVP |
| 利用者に機能を継続提供したい | Product |

MVP では、価値評価が期待した結果にならない場合もあります。計画した実証と評価を完了し、結果を記録できていれば、期待した価値が確認できなかった場合でも、その開発作業は完了と判断できます。結果を受けて継続・変更・中止するかは、別の判断として扱います。

開発は一つの分類から別の分類へ進むことがあります。目的が変わった場合は、新しい目的と完了条件を定めます。以前の目的に対する完了判定は、新しい分類へ進んだことだけで取り消されません。

## 品質を決める3つの軸

品質要求は、次の3つの軸を合わせて定めます。

1. **成果物の目的**：Sample / Experiment / PoC / MVP / Product
2. **提供段階・対象**：内部利用 / Closed Beta / Open Beta / 正式公開など
3. **実行リスク**：データ、権限、利用環境、外部への影響、失敗時の回復可能性など

提供段階は成果物の目的とは別の軸です。例えば、既存 Product のバージョン2を Closed Beta として提供できます。Product であることだけから正式公開段階だと決めたり、Beta であることだけから成果物の目的を決めたりしません。

実行リスクが高い場合は、成果物が MVP や PoC であっても、データ保護、権限境界、外部への影響、停止・復旧などに必要な対策を明確にします。検証目的を理由に、重大なリスクや安全上の懸念を放置しません。一方、リスクの低い限定環境では、運用や診断の仕組みを必要以上に作り込まない判断もできます。

## 分類ごとの品質目安

以下は計画時やレビュー時に検討する例です。プロジェクトの要求、提供段階、実行リスクに応じて、採用・省略・変更できます。

| 分類 | 例外処理・テスト・ログの目安 | 文書・保守性の目安 |
|---|---|---|
| **Sample** | 説明対象の正常系を確認する。手動確認で足りる場合がある。予期しない入力への対応やログは、説明目的に必要な範囲で扱う。 | 実行・閲覧方法や前提を必要に応じて添える。使い捨ての例なら、長期保守向けの構造を要求しない。 |
| **Experiment** | 検証したい仮説や動作を確認し、結果を再確認できる条件を残す。例外処理やログは、実験結果の解釈に必要な範囲で用意する。 | 使用した環境、条件、結果、分かった制約を記録する。実験後に保守する予定がなければ、製品相当の保守性は求めない。 |
| **PoC** | 実現可能性を左右する主要経路や前提を確認する。重要な失敗やリスクは検出できるようにし、網羅的なテストや全例外への対応は目的に応じて決める。 | 判断に必要な構成、前提、制約、検証結果を共有する。継続開発を予定する場合は、次段階へ引き継げる範囲で整理する。 |
| **MVP** | 正常系で限定した主要価値を示すことを基本とする。サンプルを使った手動確認でもよく、自動テスト、網羅的な例外処理、詳細なログを一律に必須とはしない。提供範囲やリスクに応じて追加する。 | 評価に必要な実行・利用方法と既知の制約を分かるようにする。評価後に継続する見込みやリスクに応じて、保守性への投資を決める。 |
| **Product** | 合意した機能・品質要求に対し、適切なテスト、異常時の処理、診断・記録、必要な復旧手段を整える。提供段階やリスクに応じて対象を定める。 | 利用者と保守担当者に必要な説明を用意し、変更や継続提供を支えられる構造を選ぶ。要求のない網羅性や複雑さまで自動的に求めない。 |

MVP の品質は、主要な価値を実証できることを基本としながら、目的、要求・要件、提供対象、実行リスクに応じて上下させます。「とりあえず動くものを見せて評価する」段階では、評価に必要な正常系の動作や最低限の使い方を完成条件にし、自動テストや詳細な運用機能は必要性を確認してから加えることができます。これは、それらを禁止するものではありません。

## 計画と品質条件

品質条件は、開発計画の目的・範囲・完了条件・検証方法と矛盾しないように定めます。必要な範囲で、成果物の目的、提供段階、実行リスク、採用する品質要求、既知の制約を計画または参照先に記録します。小規模な作業では、これらを完了条件や検証方法に短く含めれば十分です。

完成判定では、合意した完了条件とその検証結果を確認します。分類ごとの目安に項目があるという理由だけで、計画に含まれない品質要求を後から完成条件へ追加しません。要求の不足や改善の余地を見つけた場合は、今回の完了判定への影響と今後の提案を分けます。

要求、提供段階、リスク、完了条件、検証方法を変更する場合は、開発計画の変更管理に沿って、変更内容、影響、判断を記録します。品質水準を上下させるときも同様に、範囲、日程、必要な検証、残る制約への影響を確認します。

詳しい計画項目と完了・変更の扱いは、[開発プロセスガイドライン](./development-process-guidelines.md)を参照してください。

## レビューでの指摘

レビューでは、指摘の種類と、その指摘を受けた判定への影響を分けて考えます。指摘の種類だけで修正必須と決めず、合意済みの要求・完了条件、実際の影響、対応後に残るリスクを確認します。

指摘の種類は、主に次のとおりです。

- **要求違反**：合意済みの要求や完了条件を満たしていない状態です。
- **重大なリスク・安全上の懸念**：放置した場合に人、データ、権限、システム、外部への影響などに重大な結果を招く可能性がある状態です。
- **範囲外の改善提案**：合意済みの要求や完了条件には含まれない、将来に向けた改善案です。

判定への影響は、指摘の種類とは別に、例えば次のように決めます。

- **修正必須**：合意済みの要求・完了条件への違反があり、受け入れられる代替策や条件がない場合、または重大なリスクが未軽減で継続が適切でない場合に、必要な修正や対策を求めます。
- **条件付き許容**：影響を評価したうえで、実行環境の隔離、対象範囲の制限、権限の縮小などによりリスクを適切に抑えられる場合は、条件、残る影響、見直し時点などを明確にして継続を認めることがあります。許容の判断は、影響と条件を確認し、そのリスクを受け入れる権限を持つ判断者が行います。重大なリスクを無条件に許容するものではありません。
- **改善提案のみ**：合意済みの要求・完了条件に影響せず、重大なリスクにも該当しない範囲外の提案は、今回の必須修正にせず、必要に応じて将来の課題として記録します。

例えば、要求違反でも影響が限定され、権限を持つ判断者が明示した条件のもとで受け入れる場合は、条件付き許容となることがあります。反対に、範囲外の提案であっても重大なリスクが判明した場合は、リスクとして評価し直します。重大なリスクは、低減策と残余リスクを確認し、権限を持つ判断者が継続の可否を決めるまで、無条件で受け入れません。

表現の好みや一般的なベストプラクティスだけで、合意済みの範囲外の事項を必須修正にしません。採用する改善提案や要求・品質水準の変更は、変更管理を通じて計画と完了条件へ反映します。

レビュー判定、開発段階の移行、成果物の受け入れ・リリースは、それぞれの目的に応じて区別します。個々の判定の詳細は、開発プロセスガイドラインに従います。

## 失敗の記録とガイドラインの改訂

品質条件を満たせなかった場合や、想定外の問題が生じた場合は、規模に応じて、起きたこと、影響、分かった原因、判断、次の対応を記録します。失敗や未達は責任追及のためではなく、次の判断や改善に活かします。

実際の開発・レビューで、目安が過剰な負担を生んだ場合、重大な問題を見逃した場合、判断が分かれた場合は、その経験をもとに本ガイドラインを見直します。この文書は初版であり、すべてのケースを先回りして規定するものではありません。
