# GitLab Flow 品質ゲート方針

> 作成日: 2026-11-22
> 更新日: 2026-11-22
> 作成者: Codex

この方針は、Ateliers-Dev が採用する GitLab Flow 環境ブランチ型において、開発統合からリリースまでの品質ゲートを配置する基準を定めます。レビュー工程の共通責務は[レビュー工程と品質判定の共通方針](./review-process-guidelines.md)、方式選択は[ブランチ戦略ガイドライン](./branch-strategy-guidelines.md)を参照します。

## 基本モデル

Ateliers-Dev の標準形は、作業ブランチから開発ゲートを通過した変更を main へ統合し、候補を固定してリリースゲートを通過した内容を production へ昇格する環境ブランチ型です。

| 対象 | 保証する段階 |
|---|---|
| 作業ブランチ | 変更単位の開発・レビュー・必要な開発チェック |
| main | 開発品質ゲートを通過した変更の統合先。リリースゲート通過前の変更を含む場合がある |
| リリース候補 SHA | リリースレビューと検証を行う対象コミットの固定記録 |
| production | リリース品質ゲートを通過した内容の昇格先 |
| 正式リリースタグ | 実際にリリースした production コミットを示す版記録 |

main と production への変更は Pull Request を通じて統合します。直接 push や直接マージでゲートを迂回しません。通常のリリースごとに長期 release/* ブランチを作りません。複数バージョンを継続保守する必要がある場合は、保守対象と修正の取り込み方法を計画してから保守ブランチを設けます。

## 段階別の品質ゲート

| 段階 | ゲートで確認すること | 通過条件 |
|---|---|---|
| 作業開始前 | 成果物の目的・段階、範囲と対象外、完了条件、安全上の最低条件、レビューと検証の種類、必要な証跡と判断者を定める | 合否に必要な条件が明確で、途中で無断変更されない |
| 作業ブランチ → main | 開発レビューで要求適合、変更範囲、外部公開契約の利用、エラー処理と要求された fail-closed を確認する。変更に応じた設計レビュー、build、Unit/Fake 等を実施する | 計画で必須としたレビュー・チェックが完了し、阻害指摘が解決または権限者により処理されている |
| main での統合 | 統合済みの対象 SHA、開発レビュー結果、必須チェック、受け入れ済みの残課題を記録する | main の履歴が開発品質ゲート通過を示す。これはリリース判定の代替ではない |
| 候補の固定 | main からリリース候補の SHA を選び、対象環境・依存バージョン・受け入れ条件と対応づける | 固定した候補へ後続の main 変更を混ぜない。候補を変更したら新しい SHA として評価する |
| リリースレビュー | 候補に対して必須条件を確認し、対象版に結び付く証跡を評価する。必要かつ事前に定めた場合は、実環境での結合・E2E、配布物、更新、復旧を検証する | 必須条件の証拠が揃い、技術所見と工程判断が区別されている。条件付き通過や残余リスクの受け入れは権限者が判断する |
| 候補 → production | 昇格PRが固定候補とリリースレビュー結果に結び付いていること、阻害事項の状態、人による必要な判断を確認する | 昇格対象の内容が検証済み候補と一致する。PRマージでコミットSHAが変わる場合は候補SHAとproduction SHAの双方を記録し、ツリーの一致を確認する |
| production → 正式リリース | 保護された不変の正式タグを、承認済み production SHA に付ける。公開対象をそのタグから生成し、生成元SHA、実行記録、成果物識別子・版、取得できる場合はダイジェストを記録する | タグが合格済み production SHA と一致し、公開する成果物がそのタグのコミットから生成された証跡がある。公開物が承認済み成果物と同一であり、権限を持つ人が公開・配布を決定している |

### リリース候補と再検証

候補を選んだ後も main で開発を続けられます。リリースレビュー中に main が進んでも、固定 SHA は変えません。固定候補を昇格PRのheadにするため一時参照が必要な場合は、候補SHAを指す参照を使い、昇格PRへ取り込んだ後に役割を終えます。その参照には候補SHAの後に main へ入った変更を含めず、PRのheadが固定候補と同じ内容を指すことを確認します。

以前の証跡は、対象コード、受け入れ条件、環境、依存バージョンなど判断条件が変わらない範囲で再利用できます。候補との差分や条件変更で影響を受ける部分だけを再検証し、再利用した証跡と新たに確認した差分を記録します。候補SHAが変わった場合も、無条件に全検証をやり直すのではなく、影響と証跡の有効性を確認します。

### 昇格時の履歴整合と成果物の追跡

候補を固定する前に、現在の production の履歴と候補の関係を確認します。通常の昇格では production の現在の先端が候補の祖先であり、既存の production 修正を候補が含んでいることを条件とします。production にだけ存在する必要な修正があれば、先に main へ Pull Request で取り込み、影響する開発ゲートを通して新しい候補SHAを固定します。履歴が分岐している場合も、production 固有差分を明らかにし、候補に反映・検証するまで昇格しません。

候補固定後、昇格前に production が進んだ場合は、その追加差分を候補へ取り込み、新しい候補として影響範囲の証跡を更新します。昇格PRでは固定候補より後の main 変更を含めず、production の既存修正も欠落させません。マージ方法によりコミットSHAが変わるときは、候補SHAとproduction SHAを記録し、ツリーの一致を確認します。一致しない場合は昇格を保留し、差分をレビュー・検証して新しい候補を固定します。

正式タグは合格済み production コミットを指し、リポジトリのアクセス制御で作成後の移動・削除を防ぎます。リリース記録にはタグ、承認済みproduction SHA、生成元リポジトリとコミットSHA、ビルドworkflow/run、成果物名・版・識別子、取得できる場合はダイジェストを対応づけます。公開には、その記録で承認された成果物と同一の成果物を使用します。昇格でSHAが変わった場合は、公開物の生成元が実際のタグ／production SHAに結び付くことを別途確認します。

## 外部依存と未実施の検証

開発レビューでは、外部CLI、ライブラリ、OS、実行基盤の内部品質を無制限に監査しません。開発側の責務は、公開契約に従った呼び出し、設定・権限・入力の選択、結果処理、要求された安全な失敗です。依存先が公開仕様どおりに動くことを前提にできる範囲は、[レビュー方針](./review-process-guidelines.md)に従います。

結合・実環境試験が必要かどうかは、Review Planning で目的・リスク・完了条件に照らして事前に決めます。環境制約で実施できない場合は、対象環境、試行、観測結果、未実施の確認、再開条件を記録します。単体テストや通常CIの結果を、未実施の結合・E2E試験の証拠として扱いません。未実施が必須条件に関係する場合はゲートを通過させず、関係しない場合も不確実性を明示します。

## CI と公開処理の分離

GitHub Actions 等のCI/CDでは、イベントとブランチの対応を品質ゲートに合わせて定めます。

- 作業PRからmainへのPRでは、開発ゲートに必要なレビューと自動チェックを行う。
- 候補からproductionへの昇格PRでは、固定候補とリリースゲートの証跡を確認する。PRイベントで本番公開しない。
- mainへのpushは開発用チェックやプレビューに使い、本番公開の契機にしない。
- 正式公開は、合格済みproductionコミットに付けた保護対象のタグなど、リリース対象を一意に特定できるイベントに結び付ける。タグが承認済みproduction SHAを指すことを確認し、必要に応じて公開前に人の承認を要求する。
- 公開する成果物の生成元コミットSHA、workflow/run、成果物識別子・版、取得できる場合はダイジェストを記録し、承認済みの成果物と同じものを公開する。
- build・検証と公開処理を分け、ブランチトリガーを追加しただけで公開先や権限が変わらないことを確認する.

プロジェクトは required checks、環境保護、タグ規則、成果物の対応、手動復旧方法を自分のCI/CD設定に反映します。この共通方針は、特定リポジトリのworkflow設定を変更しません。

## 失敗・修正・復旧

- 開発ゲートの指摘は作業ブランチで修正し、main向けPRのレビューと必要なチェックを更新します。
- リリース候補に修正が必要なら、新しい候補SHAを固定して影響範囲の証跡を更新します。
- production昇格後に修正する場合は、Pull Requestで変更し、修正がmainにも必要かを判断して反映先を追跡します。
- リリース後の復旧では、対象タグと成果物を特定し、前のタグへの復旧または修正版の提供を権限者が判断します。
- 複数バージョンを保守する場合は、対象系列、修正の反映先、保守終了条件を明示します。

## プロジェクト計画への適用

各プロジェクトは、成果物の目的・提供段階・実行リスクと受け入れ条件に基づき、表中のゲートを具体化します。正式リリースを行う場合は、タグの保護・SHA照合と公開成果物の生成元・識別子の追跡を必須適用項目として具体化します。小規模な変更にすべての工程を要求するものではありません。省略した工程や必須証拠の変更は、プロジェクトの計画と変更判断に記録します.
